# Arda 1.0 Vision-to-Live Gap Report

## Purpose

This report compares the full Arda 1.0 personal-agent-ecosystem doctrine with
current source, active plans, archived design records, and checked-in runtime
projections. It exists to prevent another plan or implementation tranche from
calling a contract, unit test, projection, or UI shell a finished capability.

It does not certify the current running machine or services. Live process,
network, device, phone, and native-HUD acceptance must be re-probed during the
implementation tasks that own those gates.

## Classification vocabulary

- **Implemented:** source and focused tests exist.
- **Integrated:** the supported runtime or a canonical consumer uses it.
- **Workflow-proven:** an end-to-end fixture or operational path exercises it.
- **Live-proven:** a running external/runtime/device path was exercised.
- **Operator-accepted:** the operator used and accepted the intended surface.
- **Release-supported:** artifact, install, compatibility, documentation,
  diagnostics, privacy, and support gates pass.
- **Partial:** meaningful implementation exists but the requested behavior or
  evidence level remains open.
- **Planned/deferred:** design exists without current implementation authority.
- **Absent:** no visible production implementation was found.

## Executive verdict

Arda is not an empty architecture. It has substantial foundations:

- a canonical root runtime and service supervisor;
- durable project and run-graph contracts;
- bounded Hermes execution with actual session evidence translation;
- three project-adapter golden paths and restart tests;
- a mature Vairë memory and governance implementation;
- Personal Operations contracts, service endpoints, reminders, calendar, HUD,
  voice capture, briefs, and data export/deletion;
- governance, council, communications, research, routing, observability, and
  HUD contract surfaces.

However, the complete personal-agent-ecosystem experience is not yet proven.
The most important gap is not another subsystem. It is **composition**:

- the phone is not yet demonstrated as a first-class Arda operator path sharing
  canonical run/task/session lineage;
- the orchestrator does not yet prove dynamic task-scoped capability selection;
- multi-worker Hermes execution and local-model council deliberation are not
  demonstrated as one durable run;
- proactive personal assistance is not live-proven as a bounded event cycle;
- external-system use-to-assimilation is still deferred research;
- x402 is absent from visible source;
- Wi-Fi blood-pressure ingestion is not implemented and remains privacy-gated;
- Mirromere and expanded RELIC/CITADEL interaction remain deferred;
- native/operator acceptance is incomplete for the converged HUD and five
  universal monitor sessions.

## Current plan-estate conflict

The 2026-08-06 estate audit and Stage 6 plan intentionally narrowed Arda 1.0 to
Workbench and placed Mirromere expansion, Company Operations pilots, external
product adoption, and device work outside 1.0. That was a release-risk decision,
not a faithful statement of the full operator vision.

The new doctrine corrects the product meaning without requiring every optional
peripheral to become a mandatory installed component. The implementation plan
therefore separates:

- **required ecosystem contracts and composition paths**; from
- **optional/private-alpha capability implementations**.

This avoids both prior failure modes: an artificially narrow Workbench-only
identity and an unshippable requirement to complete every future device before
calling the kernel 1.0.

## Governance findings

### Governance mechanisms are implemented but mostly advisory

`arda-governance` exports Love Dynamics, the legacy Love Equation proxy,
JouleWork profiling, Triad, Bacon-lite, readiness, realm policy, scoring, and
evidence surfaces. Triad evaluates Aurelius/Bacon/Sun Tzu lenses and can emit
veto reasons; Bacon-lite persists validated events with batching, locking,
rotation, and backpressure behavior. This is meaningful implementation.

It is not yet a complete enforcement boundary. Triad results explicitly keep
autonomous blocking disabled, and the active realm policy describes global
rules as advisory/non-blocking. The audited source did not establish one live
runtime owner that consumes these verdicts, binds them to run transitions, and
writes authoritative allow/deny/approval receipts.

**Required correction:** name `arda-engine` or another single canonical runtime
owner as the enforcer; preserve governance crates as evaluators; bind every
deny, approval request, and allowed transition to the same run/action digest;
and prove that Hermes, Manwë, Oromë, HUD, and external adapters cannot bypass or
downgrade that decision.

### Love semantics are currently conflated in documentation and policy

`crates/spine/governance/arda-governance/src/love_equation.rs` explicitly says
the impact/reach/energy/time calculation is a legacy task-value proxy and is
not canonical Love Dynamics. Yet active rules and older documents often name a
required `love_equation` validator as though the numeric proxy were complete
human alignment.

**Risk:** agents or UI surfaces may claim “Love passed” from a low-resolution
value calculation that does not address consent, coercion, relational effect,
privacy, or language.

**Required correction:** retain compatibility fields but emit explicit
`semantic`/`source` metadata, route human-facing actions through canonical Love
Dynamics/human-impact policy, and make UI explanations distinguish the two.

### JouleWork is meaningful but not yet the complete burden model

The economics crate tracks compute, network, storage, attention, and reasoning,
with measurement provenance and confidence. Governance profiles compare
estimated and actual values. Snapshot restoration is explicitly synthetic.

The runtime accumulator is currently in memory, and
`config/runtime/runtime_governor_budget.toml` is declarative. The audit did not
find proof that those caps currently govern Manwë route choice or engine
execution transitions after restart.

**Gap:** the canonical Workbench and proactive loops do not yet prove that
operator interruption, local hardware pressure, hosted cost, and recovery work
all shape worker selection and notification behavior.

**Required correction:** an append-only run-linked resource ledger must carry
observed versus fallback measurements, reconstruct restart-safe rollups,
reconcile provider usage, enforce configured caps in the canonical execution
path, and explain any route, stop, approval, or interruption decision.

### Durable learning remains only partially closed

Varda provides ingest, query, deep analysis, external-lane evaluation/import
receipts, and Rúmil evidence evaluation. The scout/outpost boundary is correctly
advisory and has no queue, approval, or execution authority. What remains open
is the durable sequence from observation or suggestion through evaluation,
approval, a versioned `KnowledgeDelta`, Vairë ingestion, and evidence that a
real consumer used or rejected the result.

This missing closure is directly relevant to nightly assimilation: external
research must become governed proposals and measured knowledge before it can
become code or behavior.

### Council contracts prevent some authority collapse but do not prove debate

Oromë correctly marks discussion-only notes, blocks final-approval language,
restricts local inference notes to low-risk summaries, and requires a canonical
task reference before projection. Aulë defines query modes and required output
sections.

**Gap:** these are discussion and projection contracts. They do not establish
that multiple independent model workers were actually invoked, received
bounded evidence, disagreed, were adjudicated, and affected a durable run.

### The active autonomy configuration is not live autonomy proof

`config/governance/autonomy_operating_loop.toml` describes a rich twelve-stage
loop and named lanes, but it is marked `active_draft`; L3 enforcement is still
listed as pending. Configuration, generated state, and lane declarations are
not proof that the complete loop runs continuously or safely.

## Personal-system findings

### Personal Operations is one of the strongest implemented foundations

The active plan records contracts, append-only storage, capture, classification,
scheduling, completion, resume, briefs, calendar adapters, reminder receipts,
HUD, voice capture, and export/deletion implementation.

Four acceptance gates remain important:

- sub-five-second operator capture;
- restart recovery with no lost accepted capture;
- correctable sourced daily brief;
- one-week dogfood with manageable reminder burden and successful context
  recovery.

### Privacy review is stale relative to some implementation claims

The privacy review says export/deletion are absent, while the Personal
Operations plan records that those endpoints were later implemented. Other
blocking gaps remain relevant: owner-only storage, identity enforcement,
retention controls, adapter egress receipts, backup scope, and wellness misuse
tests.

**Required correction:** repeat the review against current source before any
health-device adapter begins.

### Health support must remain evidence-typed and non-clinical

The archived Mirromere record has a strong boundary: validated device,
self-report, manual entry, and experimental derived signals stay distinct. It
also explicitly rejects camera-derived blood pressure as clinical truth.

This should be retained, but the document's old recommendation for a separate
`arda-mirromere-health` crate should not be adopted automatically. The existing
Personal Operations, Vairë, outpost protocol, and adapter boundaries should be
reused first.

## Interaction findings

### Phone is a transport gap, not a new authority problem

Hermes Gateway already supports messaging platforms, and Arda has Oromë
communications semantics. The missing piece is a tested bridge from an
authenticated mobile conversation to canonical Arda objective/run/task IDs,
status, approvals, cancellation, and result summaries.

The bridge must preserve:

- one operator identity;
- platform/chat/thread projection metadata;
- idempotency and replay;
- concise phone summaries with deep links or stable references;
- asynchronous progress without creating a second queue;
- recovery after gateway or Arda restart;
- no raw private prompt or health memory broadcast.

Discord may remain a transport, but its server/channel organization should not
be mistaken for Arda's council or task model. Telegram or another supported
Hermes Gateway transport may be simpler for personal operation; the contract
must remain transport-neutral.

### HUD work is substantial but currently dirty and incomplete

The repository contains a large in-progress HUD monitor-surface tranche with
modified and untracked TypeScript, React, Tauri, schema, and state files. It
must be preserved and reconciled rather than overwritten by this documentation
work.

The active monitor plan still requires native acceptance. The report therefore
does not count those dirty files as accepted baseline functionality.

## External-system findings

The deferred integration research already establishes the correct principles:
MCP/OTLP/CalDAV foundations, adapter-first products, optional sidecars,
license/SBOM review, failure tests, and removal instructions.

What is missing is the **operational assimilation loop** that the operator now
requires:

```text
candidate -> canonical evidence -> measured need -> isolated adapter/spike
          -> usage evidence -> clean-room/native proposal -> tests
          -> governance decision -> bounded landing -> rollback/removal
```

The overnight cadence should run collection, evaluation, comparison, and patch
preparation. It must not create a broad unattended dependency updater or copy
unknown-source code into Arda.

## Economic findings

Commercial types and reference adapters exist, and Workbench can complete
external project artifacts. No visible x402 implementation was found.

The correct sequence is:

1. define an optional `EconomicCapability` contract;
2. prove offline quotes, budgets, approval scope, idempotency, receipts, and
   compensation;
3. add a mock x402 transport;
4. security-review wallet/key custody separately;
5. permit a testnet or tightly bounded live payment only after explicit operator
   approval;
6. keep economic capability absent from personal tasks unless requested.

## False-completion root causes

Repeated overstatement is enabled by several structural patterns:

1. plan checkboxes mark contract-level work without naming the maturity level;
2. generated `core/state` projections look operational even when their producer
   is inactive or deterministic;
3. unit tests prove local logic but are summarized as end-to-end behavior;
4. UI components are exported without being mounted in the native path;
5. model or agent self-reports are accepted without independent artifact checks;
6. transport projection is confused with canonical state;
7. historical live evidence is reported as current state;
8. dirty or untracked implementation is silently counted as accepted baseline;
9. optional capabilities are alternately treated as universal requirements or
   removed from the product identity entirely.

## Required completion discipline

Every plan task and status report must record:

- capability and owning authority;
- achieved maturity level;
- exact source/tests/runtime evidence;
- whether evidence is fixture, live, or operator acceptance;
- unsupported and degraded behavior;
- next missing maturity level;
- task-specific acceptance tags;
- whether any author/agent self-report was independently verified.

A checkbox should use wording such as:

> Implemented and focused-tested; not yet root-composed or phone-accepted.

rather than:

> Complete.

## Minimum 1.0 vertical proofs

The implementation plan should not close until these cross-domain proofs exist:

### Proof A — personal continuity from phone

Phone capture -> canonical personal event -> sourced resume/brief -> reminder ->
phone acknowledgement -> restart -> same state.

### Proof B — governed external project

Phone objective -> project contract -> plan/run graph -> Hermes worker ->
project-native verification -> review -> phone acceptance/revision -> artifact
and receipts -> restart.

### Proof C — useful local council

Materially uncertain objective -> hosted proposer -> at least two independent
local critics -> persisted disagreement -> adjudication -> governance decision
-> execution or explicit stop. The local models must perform observable useful
work rather than return health checks.

### Proof D — proactive bounded care

A fresh operator-authored condition becomes eligible -> quiet/fatigue/Love/
JouleWork/action-class evaluation -> one appropriate message or reversible
action -> acknowledgement/deferral -> no duplicate after restart.

### Proof E — governed external-system assimilation

External candidate -> provenance/license evidence -> isolated adapter/spike ->
measured use -> proposal -> approval/rejection -> bounded patch or clean removal
-> replay-safe receipt.

### Proof F — optional economic attachment

A non-economic task proves no payment capability is present. A separate opt-in
fixture attaches quote/budget/approval/payment receipt semantics without
changing the base task or permitting funds movement.

### Proof G — optional validated device

After renewed privacy approval: one specific blood-pressure device or export
fixture -> typed personal observation -> duplicate/stale handling -> private
trend projection -> operator correction/export/delete -> no diagnosis or
unapproved notification. Live device proof is separate from fixture proof.

## Recommended sequencing

1. Freeze doctrine and capability composition.
2. Bind phone/Hermes Gateway to canonical Arda sessions.
3. Prove one multi-worker run and local council role.
4. Complete Personal Operations acceptance and proactive-cycle dogfood.
5. Activate the adapter/assimilation pipeline.
6. Add optional economic and validated-device capability contracts behind
   explicit gates.
7. Finish HUD/native monitor convergence as a projection of those real runs.
8. Reconcile Stage 5/6 release engineering around the corrected product promise.

## Final verdict

The system has enough real foundation to justify convergence rather than
abandonment or another rewrite. The next work should not add more mythology or
parallel frameworks. It should make the already-implemented kernel coordinate
real phone, worker, personal, council, adapter, and optional capability flows
under one durable truth model.

Arda 1.0 is not complete today. It becomes credible when these flows are
operator-reachable, restart-safe, failure-proven, and reported without
collapsing implementation into acceptance.
