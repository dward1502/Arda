# Arda Whole-System Completion Program

## Product outcome

Arda is the operator's coherent personal system across conversation, personal life, memory, research, projects, models, devices, and interfaces. It must reduce the burden of remembering, coordinating, checking, and recovering—not turn all of those concerns into automated project execution. The [product doctrine](../architecture/ARDA_1_0_PERSONAL_AGENT_ECOSYSTEM.md) defines that outcome; this program must not narrow it.

Autonomous execution is one capability: the operator states goals and constraints once; Arda retrieves context, connects real projects, applies authority, schedules and places bounded execution, verifies results, revises failures, and preserves continuation. Completing that capability alone does not complete Arda.

## Canonical operating loop

1. Observe an operator request, failure, stale plan, audit finding, degradation, or cited external finding.
2. Retrieve exact project state, active plans, receipts, Vairë continuity, source, and current external evidence.
3. Frame an outcome contract with acceptance, scope, authority, risk, budget, and stop conditions.
4. Decompose dependency-aware tasks tied to real project contracts.
5. Authorize through existing policy; ask only when authority or intent genuinely blocks work.
6. Schedule through canonical Arda schedule authority.
7. Place deterministic tools or admitted provider capacity through Manwë.
8. Execute through Workbench and the owning adapter/tool boundary.
9. Verify declared checks and human-visible artifacts.
10. Review independently where risk or uncertainty requires it.
11. Close, retry, revise, replan, defer, or request one concrete decision.
12. Record context use, outcomes, corrections, and reusable learning with provenance.

## Execution order

Gates 1–5 below describe execution, placement, project, and improvement dependencies; they are not an exhaustive definition of Arda or a universal serial queue. Dependency-ready personal-system work proceeds through its existing owner alongside these repairs. Gate 6 requires the broader product evidence above as well as the autonomous evidence; no automatic promotion follows from passing Gates 1–5.

### Gate 1 — Complete the autonomous loop

Finish the five milestones in the [Autonomous Task Completion Program](autonomous-task-completion/README.md). Do not replace installed acceptance with more isolated queue, schema, projection, or UI slices.

Exit: one real operator-authored, multi-project objective survives scheduling, restart, failure, critic revision, and cross-session continuation to verified close with explicit operator acceptance.

### Gate 2 — Route real workers

- connect canonical queued work to Manwë placement;
- enforce capability, privacy, health, context, cost, and tool constraints;
- exercise deterministic, local, subscription, and hosted fallback routes where policy allows;
- record actual provider/model/resource receipts without silently changing authority.

Exit: real canonical work demonstrably uses admitted capacity according to policy.

### Gate 3 — Connect the project fabric

- inventory real projects and classify ownership/scope;
- generate and review exact project contracts;
- attach approved projects through canonical Workbench authority;
- maintain current-state audits and prioritized backlogs without creating parallel queues.

Exit: production authority contains real bounded projects rather than proof fixtures.

### Gate 4 — Activate daily improvement

- derive questions from active objectives, failed checks, project audits, and dependency drift;
- gather current cited evidence;
- promote worthwhile findings into outcome contracts;
- execute eligible improvements through the same completion loop;
- carry unfinished work forward across scheduled cycles.

Exit: seven consecutive installed cycles include at least one verified improvement, one justified no-change result, and one correctly rejected idea.

### Gate 5 — Govern external assimilation

- discover one candidate for a named Arda need;
- preserve source, license, digest, SBOM, permission, and resource evidence;
- evaluate it in the declared isolated boundary;
- choose adapter retention, package adoption, selective implementation, or rejection;
- verify the result and retain rollback/removal evidence.

Exit: one real candidate reaches governed verified use or justified rejection across restart.

### Gate 6 — Whole-system acceptance

Establish the product doctrine's base experience across shared conversation, personal capture/resume, scoped and correctable memory, useful research, philosophical judgment, appropriate model/device use, and truthful interfaces, as well as project execution. Retain accepted evidence with its exact scope; test missing connections without gratuitously replaying consequential actions. Optional distributions remain optional, not silently abandoned or prerequisites for every capability.

For autonomous work, also exercise unattended scheduling, correction, evidence-backed closure, and useful daily improvement. The operator decides whether the connected personal system materially reduces burden. An unattended execution loop alone cannot satisfy this gate.

## Non-negotiable boundaries

- Tests and schemas are engineering evidence, not product completion.
- A timer firing is not proof useful work occurred.
- A report is not an improvement unless it drives a verified outcome or justified no-change decision.
- A queue record is not complete until acceptance passes.
- UI, Hermes, systemd, and generated projections consume canonical authority; they do not create parallel task truth.
- Dirty repositories remain read-only until ownership and work in progress are understood.
- Consequential external action, credential use, purchases, public posting, destructive changes, and broad deployment remain explicitly gated.
- Ambient Agent, Mirromere, RELIC, sensors, and physical outposts remain downstream until Core Arda is repeatedly useful and accepted.
