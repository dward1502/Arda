# Arda Whole-System Completion Program

## Decision

This is the active implementation authority for completing Core Arda. It supersedes the rejected reduction of usefulness to a short conversational demonstration.

Arda's target behavior is:

> The operator states goals and constraints. Arda continuously discovers relevant work, connects it to durable context and real projects, schedules and places bounded execution, verifies and reviews its own results, revises failed work, and continues across restarts until the defined outcome is complete or a genuine operator decision is required.

The operator should not need to repeatedly assign obvious next tasks, inspect internal queues, remind Arda of unfinished implementation, or discover that a technically completed slice did not satisfy the original goal.

## Human-visible completion contract

When this program is complete, the operator can:

1. state a goal, defect, concern, or desired outcome once through Hermes or the native Arda surface;
2. see the system recover relevant conversations, plans, receipts, repositories, and current runtime state, using Soterion metadata where it speeds file discovery;
3. see a concrete definition of done, bounded work breakdown, dependencies, authority class, schedule, provider choice, and expected cost;
4. allow safe, reversible work to proceed automatically under declared policy;
5. receive review requests only for consequential actions, unresolved intent, material risk, spending beyond budget, or repeated failed attempts;
6. leave and return while Arda continues scheduled work and preserves exact state across process, host, and model changes;
7. inspect evidence showing what changed, what checks passed, which reviewer examined it, what remains, and why the system stopped or continued;
8. have all declared projects and system components reviewed on a recurring basis for unfinished work, stale assumptions, defects, and better current approaches;
9. receive implemented and verified improvements—not merely suggestions or status prose—from the daily improvement loop;
10. correct, pause, reprioritize, or revoke any objective without creating a parallel authority.

## Canonical operating loop

All work uses one lineage:

1. **Observe** — operator request, failed receipt, stale plan, project audit, runtime degradation, or cited external finding.
2. **Retrieve** — use Soterion metadata to narrow file discovery, then combine exact project state, active plans, queue history, receipts, Vairë continuity, source inspection, and current external evidence.
3. **Frame** — produce an outcome contract with acceptance criteria, scope, risk, budget, and stop conditions.
4. **Decompose** — create dependency-aware tasks tied to real project contracts.
5. **Authorize** — apply policy; do not ask for permission where existing policy already grants bounded authority.
6. **Schedule** — run now, at a durable future time, or on a recurring cadence through canonical Arda scheduling.
7. **Place** — select deterministic tools first, then appropriate local, subscription, free-cloud, or paid-cloud capability through Manwë.
8. **Execute** — use Workbench adapters and explicit project boundaries.
9. **Verify** — run declared checks and inspect actual artifacts/runtime behavior.
10. **Review** — use an independent role/model when material risk or uncertainty warrants it.
11. **Continue** — close when criteria pass; otherwise revise, retry, re-plan, or escalate with a concrete decision.
12. **Learn** — retain corrections, failure classes, successful routes, project knowledge, and reusable procedures with provenance.

### D. Daily research and improvement

Authority: [Daily Research and Improvement Loop](DAILY_RESEARCH_IMPROVEMENT_LOOP.md)

### E. External capability assimilation

Use the existing external-capability, AIPKG, and Engine assimilation contracts to evaluate and adopt open-source repositories, packages, adapters, tools, services, and techniques. ## Program gates

- Tests and schemas are engineering evidence, not product completion.
- A timer firing is not proof that useful work happened.
- A generated report is not an improvement unless it drives a verified outcome or a justified no-change decision.
- A queue record is not complete until its acceptance criteria pass.
- An LLM self-review is not independent if it reuses the same role, context, and failure assumptions without challenge.
- Consequential external action, public posting, purchases, credential use, destructive changes, and broad deployments remain explicitly gated.
- Dirty repositories are inspected read-only until their ownership and work-in-progress are understood; Arda does not overwrite operator work.

## Immediate implementation slice

The first code slice is not another UI demo or a larger queue silo. It is one vertical composition proof across existing owners:

1. start from one real Rúmil finding, Warden/Varda evidence item, or operator objective with a canonical Core `objective_id`;
2. resolve its real project contract and acceptance conditions, using Soterion metadata only to accelerate file discovery;
3. create an Engine RunStore graph and preserve the same objective/run identity through Workbench execution;
4. use governance for semantic authority, Engine for worker lifetime/placement, and Manwë only for the provider/model route when inference is needed;
5. execute through the owning deterministic tool, Hermes worker, external-capability adapter, or AIPKG boundary rather than bypassing those contracts;
6. return Varda/Rúmil evidence to an explicit verifier/reviewer, then let Engine emit the terminal transition and queue projection;
7. record consumed context/outcome in Vairë and schedule a concrete continuation when acceptance fails;
8. kill and restart the process mid-run, then prove the same lineage resumes to verified closure without another operator task.
