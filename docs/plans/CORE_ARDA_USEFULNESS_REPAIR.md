# Core Arda Usefulness Repair

## Product promise

An operator can speak or type through Hermes or the HUD, and Arda will:

1. recognize a capture, question, context request, or consequential request;
2. save it under the correct durable authority;
3. return one trustworthy next action or source-grounded answer;
4. request exact review where authority requires it;
5. expose execution and receipts;
6. survive restart and restore the same context through Hermes/HUD.

This plan owns composition and usefulness. Domain contracts remain owned by their existing crates and services. It must not create another queue, memory store, research authority, policy system, or runtime.

## Holds

Until the operator accepts the core journey:

- Mirromere remains stopped;
- no RELIC expansion, sensors, physical outposts, or commercialization execution;
- no external agent account, Moltbook account, wallet, funded account, trade, payment, or public posting;
- economic and agent-community objectives remain reviewed research/planning only.

- [ ] Define one typed source-truth next-action projection owned by core Arda, not the HUD.
- [ ] Read current operator-authored queue tasks, Personal Operations items, active Workbench runs, and current research holds.
- [ ] Exclude historical, stale, terminal, inferred-without-review, and future-gated objectives from automatic selection.
- [ ] Return one item with source reference, reason, freshness, authority state, and the smallest next operator action.
- [ ] Expose it through the harness and consume the same projection in Hermes and HUD.
- [ ] Add empty, blocked, stale, restart, and conflicting-priority regressions.

Visible result: Arda says what to do next and why, instead of presenting independent subsystem counts.

## Phase 3 — Natural operator intake

Visible result: the operator does not need to remember internal command syntax for ordinary use.

## Future-gated objectives

### Economic agency

Before any `$20` or `$250` budget is attached, require:

- exact account/wallet/custody choice;
- asset, chain/network, and jurisdiction/risk review;
- maximum per-action and cumulative loss budget;
- allowlisted action classes and counterparties;
- quote/expiry, replay protection, accounting, dispute/compensation, and tax export;
- simulation/testnet evidence;
- explicit operator approval for the first funded action.

### Arandur agent-community listening post

Before any Pi5 deployment or Moltbook presence, require:

- source/licensing/API/account-policy research;
- clear Arandur identity and disclosure that it is an Arda-operated agent;
- private-data and operational-detail redaction policy;
- read/listen-only initial mode;
- provenance-preserving idea intake into Varda/Rúmil review;
- rate, attention, and manipulation-resistance budgets;
- explicit account creation, public posting, and deployment approval.

## Completion rule

This plan is not complete from builds, fixtures, service health, or documents. Completion requires the operator to use and accept the full core journey without terminal intervention. Optional economic agency and the agent-community listening post do not block core acceptance and remain separately gated.
