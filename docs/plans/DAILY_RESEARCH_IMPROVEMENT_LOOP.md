# Daily Research and Improvement Loop

## Outcome and current state

Arda derives bounded questions from real goals, project drift, failures and current
external evidence; promotes only justified findings; verifies eligible improvements;
carries unfinished work forward; and stays quiet when no change is warranted.
This is not a daily digest or continual feature-generation mandate.

Partial. The existing [nightly hygiene work](../operations/RUMIL_NIGHTLY_HYGIENE.md)
records a script-only Hermes 03:17 job, finding lifecycle, material-change/weekly
reminder reporting, read-only budgets and no repair executor. Pre-existing dirty
Engine next-action integration offers fresh complete findings for review; it is
not evidence the installed daemon consumes them. Preserve that work. This docs
pass did not inspect/change scheduler configuration or deploy the Engine changes.

The September 15 user-manager inspection found the legacy autopilot and external-
source-lane timers inactive. September 7 “active autopilot” claims are historical;
do not reinstall old Warden/JSONL-writing units just to activate this plan. Full

owns remaining competing-writer retirement, not this plan.

## Canonical cycle

1. Read approved project/objective/plan/receipt/runtime authorities and use Soterion
   only to narrow discovery. Include operator interests and previous corrections.
2. Frame a bounded question tied to a named project/objective and a decision it can change.
3. Retrieve current primary sources where possible. Retain URL/title/time/claim,
   applicability, uncertainty, contradictions and content digest where appropriate.
4. Emit `no_change`, `knowledge_update`, `task_candidate`, `urgent_review` or
   `blocked_research`. Snippets and research findings are not execution authority.
5. Deduplicate and submit authorized candidates through authenticated Engine
   ObjectiveStore intake. Consequential action requires its existing approval.
6. Execute/verify/review through the existing loop, retain continuation across ticks,
   and feed accepted outcomes/corrections into Vairë with provenance.
7. Brief only material verified outcomes, ongoing work, exhausted failures, useful
   rejection/no-change and genuine decisions. No repeated “all clear” unless requested.

  Expose last useful cycle and partial/failure state, not only successful process exit.
- [ ] D2 — Generate questions from active objectives, connected projects and failed

- [ ] D3 — Bind retrieval/finding identities and freshness, citations, lawful digests,
  contradictions and relevance to a decision. Repeated/unchanged findings do not
  create duplicate objectives; inadequate sources produce explicit blocked research.
- [ ] D4 — Qualify installed review visibility and the governed finding→objective
  pivot: exact scope/evidence digest, project contract, authority, budget, dedupe and
  acceptance coverage. A next-action “review” is not admission or repair permission.
- [ ] D5 — Carry one approved real remedy through isolated execution, declared checks,
  independent review where required, rollback evidence and re-audit. Support bounded
  code/docs/config/dependency/test/procedure work through the same project authority;
  deployment plans are not approval to deploy.
- [ ] D6 — Link accepted change, rejection/no-change and rework to finding lineage and
  Vairë. Let verified outcomes adjust questions/source weights without overriding
  operator correction or silently expanding authority.

## Gate 4 — Seven-cycle acceptance

Do not mark this gate from seven rapid test invocations. Use seven consecutive
installed daily cycles with timestamps and durable lineage after prerequisites pass.

- [ ] G4.1 — Record every cycle, continuity across restart and unfinished work resuming
  without a new operator task; missed/incomplete cycles remain visible rather than
  being counted as successful empty runs.
- [ ] G4.2 — Every external claim has source/freshness evidence and every promoted
  action retains policy/approval/project/budget lineage.
- [ ] G4.3 — Include at least one verified improvement in a real connected project
  and a follow-up audit showing its effect.
- [ ] G4.4 — Include a justified no-change finding and an unsafe/low-value idea
  correctly rejected by policy/review.
- [ ] G4.5 — Briefs distinguish proposed, in progress, blocked and verified outcomes;
  actual delivery/readability and operator reduced-burden acceptance are recorded.

Exit gate: useful daily outcomes and justified restraint, not timer activation or
an accumulating report directory. Read-only audit work can proceed before Gate 1;
autonomous mutation uses the existing execution safety gates.
