# Arda Digital Organism Program

## Decision and purpose

Arda is a sovereign distributed digital-organism runtime. It composes heterogeneous conversational agents, model workers, memory, evidence, supervision, governance, sensing, and future physical nodes into one coherent adaptive system.

Hermes Agent supplies the fast-moving conversational and worker runtime: sessions, tools, skills, profiles/Bots, model calls, delegation, gateway surfaces, plugins, MoA, and Linux Foundation A2A transport. Arda owns organism identity, node enrollment, semantic capability contracts, workload placement policy, durable context, collective memory, authority, homeostasis, recovery, cross-node receipts, and embodiment boundaries.

The program does not compete with Hermes or create another general agent framework. It activates and aligns existing Arda anatomy around one living mesh.

## Human-visible north star

An operator submits one objective through any accepted Arda/Hermes surface. Arda restores the relevant organism context, selects the smallest capable roles, places them on currently suitable nodes, carries work and evidence across node boundaries, survives one node loss without inventing success, converges on a verified result, records what was used and learned, and shows the real topology and receipt chain. Moving the same node contract to stronger hardware improves placement and execution without redesigning the organism.

## Existing foundation to salvage

- `arda-orome`: A2A/A2H envelopes, threads, TTL, signatures, provider dispatch, capability registry substrate, operator bridge, and outcome receipts.
- `manwe`: governed provider/model routing and adaptive route evidence.
- `arda-engine`: service supervision, Hermes worker execution, cancellation, restart reconciliation, and run receipts.
- `arda-vaire`: canonical memory, correction, supersession, retention, persona/context projection, and recall policy.
- `arda-varda`: evidence ingest, provenance, comparison, contradiction, and governed research.
- `arda-governance`: authority classification, approvals, and policy contracts.
- `arda-aule`/Prometheus/Arandur: observability, proposals, planning, queue analysis, council, and operator review surfaces.
- `arda-outpost-protocol`: typed observations, presence, device intents, and receipt-backed physical boundaries.
- Hermes `arda-operator-bridge`: authenticated ingress, continuity metadata, and private reminder delivery.

Stage 0 must classify each foundation as **reuse**, **adapt**, or **archive** from live source and runtime evidence. No component is preserved only because it has a mythic name, tests, or documentation.

## Program invariants

1. One canonical authority per concern; no parallel queue, memory, topology, approval, or receipt world.
2. Standard transports are preferred: Hermes/Linux Foundation A2A for agent interoperability, MCP for tools, and authenticated local APIs for bounded host integration.
3. Arda semantic envelopes may add lineage, authority, expiry, capability, resource, and receipt requirements around a standard transport; they do not fork the transport protocol.
4. Nodes are capability/resource identities, not hard-coded hostnames or model names.
5. Missing, stale, offline, interrupted, and unknown are valid states.
6. Process-local delegation is not durable execution. Arda must reconcile or mark unknown after process loss.
7. Model votes, Bot discussions, MoA references, and council outputs are evidence, never approval.
8. Vairë remains the canonical durable continuity owner. Hermes profile memory is scoped conversational working memory, not organism truth.
9. Aulë/HUD/RELIC render source-backed state and never mint work or health.
10. Every stage exits through a demonstrable vertical behavior, not only contracts, tests, services, or projections.

## Evidence ladder

Each stage reports separately:

`documented → implemented → focused-tested → root-composed → installed → running → cross-node-proven → operator-accepted`

No lower state satisfies a higher one. Simulated nodes prove protocol behavior, not hardware delivery. A listener proves reachability, not successful inference or work completion. A provider response proves neither task authority nor operator acceptance.

## Completion

This program is complete only when the Stage 7 living mesh is repeatedly useful and the Stage 8 node contract has been demonstrated on at least one stronger or differently constrained hardware target without architectural rewrites. Hardware fabrication, public deployment, accounts, payments, and commercialization are not program completion criteria.

Implementation ownership, branch order, dirty-worktree protection, and review gates are defined in [WORKSTREAMS.md](WORKSTREAMS.md).
